# Order: богатая доменная модель

`Entities/Order` — Doctrine aggregate root; `Entities/OrderItem` — его позиции.
Существующие `orders`, `order_items`, PK/FK, номера yymmddNN и JSON журнала сохранены.
Схема не менялась, миграция/повторный импорт для этого рефакторинга не нужны.

## Правила и слои

- Order проверяет допустимость редактирования, версию, отмену, БН после оплат,
  непустой состав, принадлежность/повторы позиций и изменение доставки/комментария.
- OrderItem применяет цену и скидку через Decimal. `OrderItemData` — входные
  доменные значения, не Request DTO; проверяет количества, цену и диапазон скидки.
- Сущности не знают Request, сессию, Twig, SQL, EntityManager и changelog.
- CreateOrder заполняет CreateOrderDto.products сущностями Product из ProductRepository, по ID,
  заново при каждом вызове (переданные ранее данные продуктов не используются).
  Все товары с родителями читаются одним getByIds(array_column(lines, 'productId')).
  Повторяющиеся позиции одного товара сохраняются отдельно, повторные ID не дают запросов.
  Order::create() собирает позиции из lines и products, выбирает цену справочника,
  если входная цена null, преобразует Decimal и передаёт проверки/скидку в OrderItemData/OrderItem.
  DTO не сохраняется в сущности; она не обращается к репозиторию и не знает HTTP/сессию.
  Остальные поля CreateOrderDto readonly; products — заполняемое сервером обогащение.
  UpdateOrder аналогично заполняет UpdateOrderDto.products одним getByIds() с fetch-join
  родителя, каждый раз заменяя входной массив products. Репозиторий не фильтрует доступность:
  Order проверяет Product::isAvailableForOrder() при сборке новых позиций.
  Order::update() проверяет принадлежность позиции, выбирает исторический снимок
  неизменившегося товара (даже отключённого/без FK) либо загруженный новый продукт,
  собирает OrderItemData и вызывает общий механизм revise().
  Поля обновления readonly, кроме серверного products. При ошибке состав и версия
  не меняются; no-op не увеличивает версию и не создаёт журнал.
  Оба use case сохраняют заказ и записывают changelog в общей транзакции.
- OrderRepository загружает Order с позициями под PESSIMISTIC_WRITE и обновлением
  identity map, сохраняет через EntityManager с cascade persist / orphanRemoval.
  Выдача номера пока использует DBAL в репозитории.
  Продукция для CreateOrder/UpdateOrder загружается как сущности в ProductRepository.
  Покупателя CreateOrder получает как сущность из CustomerRepository.
- OrderViewRepository читает список, карточку и форму редактирования через DBAL.
  Справочники формы читаются в ProductCatalogRepository и CustomerViewRepository
  соответствующих доменов; отдельные OrderEditRepository/OrderFormRepository удалены.
- Расчёт итогов остаётся единственным OrderFinancialCalculator с Decimal.
  Новые операции оплаты/отгрузок/смены статуса этим рефакторингом не вводились.

Order.customer — nullable ManyToOne к Customer (существующая таблица customers).
Колонка customer_id и ON DELETE SET NULL сохранены; каскадной записи/удаления покупателя нет.
Имя и телефон в заказе остаются историческими снимками, не заменяются текущими данными Customer.
OrderItem.product — nullable ManyToOne к Product (существующий product_id, ON DELETE SET NULL).
Нет cascade persist/remove товара. Имя, группа, единица и цена позиции остаются историческими
снимками. OrderItemData принимает Product и, при сохранении старой позиции, отдельный снимок.
При удалённом товаре Product = null, но снимок остаётся обязательным. Данные справочника
не заменяют снимок при редактировании той же позиции, даже если товар отключён.
Подробнее: [Product](../Products/entities.md).
createdAt хранится как DateTimeImmutable / DATETIME, в карточке отображается d-m-Y H:i:s
(например, 25-09-2026 12:16:03); форматирование не переносится в сущность.

## Оплаты

Order.payments — OneToMany к Entities/OrderPayment, существующая таблица order_payments.
Составной PK (source, source_id), FK order_id и ON DELETE CASCADE сохранены.
Нет cascade persist/remove или orphanRemoval: редактирование заказа не изменяет оплаты.
Сценарий внесения/удаления оплат здесь не реализован.

Order::hasPayments() проверяет положительную prepayment либо хотя бы один положительный
OrderPayment. Нулевые/отрицательные платежи сами по себе не блокируют БН; возврат,
обнуляющий сумму, не отменяет существование положительного платежа (прежнее правило).
В update/revise/assertEditable больше нет внешнего флага hasPayments и отдельного
OrderRepository::hasPayments(). DBAL read model формы по-прежнему выставляет признак
для отображения; серверная проверка живёт в сущности.

Контроллер принимает ID, а findForUpdate загружает Order/позиции и обновляет коллекцию
оплат в одной транзакции под PESSIMISTIC_WRITE с HINT_REFRESH. Оплаты выбираются
отдельным fetch-join запросом, чтобы не перемножать строки позиций и платежей.
Уже инициализированная коллекция также обновляется. Будущие сценарии записи оплат
должны брать блокировку того же Order перед изменениями.

## Транзакции и позиции

Сохранение выполняется только в транзакции. Flush предшествует чтению снимка для
журнала. Ошибка журнала откатывает flush и номер; identity map очищается, чтобы
отменённые изменения нельзя было случайно сбросить позднее.

МарияDB проверяет UNIQUE(order_id, position) немедленно. При добавлении/перестановке
репозиторий временно переводит старые позиции в отрицательный диапазон и синхронизирует
original position в UnitOfWork; ORM затем записывает положительные позиции и удаляет
orphans. Это деталь хранения, не метод сущности. Всё происходит в одной транзакции.
При изменении только адреса или цены эта стадия не нужна. ID оставшихся строк неизменны.

edit_version увеличивается сущностью только при реальном изменении. Конфликт —
доменный OrderVersionConflict, middleware отображает его в HTTP 409.

Проверки: чистые unit-тесты Order без БД, существующие HTTP-сценарии создания и
редактирования, DB-тесты отката после flush при ошибке журнала, metadata validation.
