# Создание заказа

## Границы слоёв

`OrderController` отвечает только за HTTP: передачу данных в шаблон, вызов use case и redirect/JSON-ответ. В нём нет `Connection`, SQL, ручного разбора полей, проверки пользователя или CSRF.

Право `LEGACY_DIVISION` для раздела 220 пока проверяется атрибутом `IsGranted` на классе. Firewall требует `ROLE_USER` для `/orders`. `IdentityUserResolver` передаёт текущего пользователя по типу аргумента, без `CurrentUser`. Общий `CsrfTokenListener` проверяет изменяющие запросы авторизованных пользователей с сессионным firewall до разбора DTO; инфраструктурные атрибуты в action не нужны. Детали общей политики — `.knowledge/Application/http-middleware.md`.

`DomainExceptionListener` централизованно преобразует только `\DomainException` в HTTP 400. Неожиданные ошибки не перехватываются контроллером и остаются серверными ошибками.

Данные для экрана создания заказа получает `OrderFormView`. Он собирает DTO для Twig, делегируя чтение продукции `ProductCatalogRepository`, а заказчиков — `CustomerViewRepository` из соответствующих доменов.

Оба репозитория работают только с новой application database. Legacy database в создании заказа не используется. Отдельного `OrderFormRepository` нет.

Варианты продукции для формы загружаются одним read-запросом при открытии экрана. Выбор группы обрабатывает `order-form` Stimulus-контроллер локально, без HTMX-запроса; это исключает зависимость от момента инициализации HTMX после входа. В списке показывается только чистое название цвета/варианта — без цены и технической единицы измерения legacy.

## DTO и двухшаговая отправка

Имена новых HTML/JSON-полей совпадают с DTO: `productId`, `unitPrice`, `customerId`, `desiredAt`, `shippingAddress`, `shippingCost`.

Оба шага отправляются JSON-ом через общий Stimulus `json-form` controller. `POST /orders/draft` получает `Application/Controller/Order/Dtos/OrderDraftDto`: типизированные `CreateOrderLineDto[]` и `markup`. Вложенные позиции валидируются, числовые идентификаторы и наценка приводятся к int; количество, цена и скидка остаются десятичными строками. Валидный состав сохраняется в сессию как массив. Ответ HTTP 200 содержит `location` следующего экрана.

`POST /orders` получает только JSON с заказчиком и доставкой: общий `RequestDtoResolver` разбирает и валидирует `OrderCustomerDto` по `RequestDtoInterface`. Прикладной `Domain/Order/UseCases/CreateOrderFromDraft` восстанавливает и валидирует `OrderDraftDto` из массива сессии через `parseArrayToDto()`, собирает `CreateOrderDto`, вызывает use case и очищает черновик после успеха. Состав и наценка всегда берутся только из сессии: поля второго POST не могут подменить их, даже если присланы JSON-ом. Отдельного resolver заказа нет; `CreateOrderDto` — вход use case без HTTP-интерфейса.

`Domain/Order/Services/OrderDraftSession` инкапсулирует ключ сессии, сохранение массива черновика, проверку наличия и очистку. При ошибке валидации или сохранения черновик остаётся для повторной попытки. Универсальный парсер не знает о черновиках заказов.

После успешной записи черновик всегда удаляется; ответ HTTP 201 содержит `id` и `location` карточки. JavaScript открывает адрес из `location`. При ошибке черновик остаётся; сообщение показывается на текущей странице, поля не сбрасываются, отправку можно повторить. Пустые/невалидные позиции и отсутствующие обязательные поля дают HTTP 400. Повторное создание с уже очищенным черновиком отклоняется. `GET /orders/new/customer` без черновика возвращает к продукции.

`assets/lib/json_form.js` собирает вложенные строки формы в компактный JSON-массив (в том числе после удаления строк), сохраняет десятичные значения строками и передаёт CSRF через `X-CSRF-Token`. Контроллер `json-form` блокирует повторную отправку во время запроса. `JsonExceptionListener` возвращает JSON-объект `message` для ошибок JSON-запросов, сохраняя HTTP-статус; внутренние ошибки дают 500 без раскрытия подробностей.

Клиентские HTML-ограничения (`required`, `min`, `max`, `step`) показывают русские сообщения независимо от языка браузера: событие `invalid` перехватывается в capture-фазе, устанавливается `setCustomValidity`, а при вводе/изменении поля сообщение сбрасывается для повторной проверки.

`RequestDtoParser` читает JSON самостоятельно, рекурсивно приводит скаляры вложенных DTO и возвращает HTTP 400 при ошибке десериализации/валидации. Дата `Y-m-d` разбирается с полуночью, без добавления текущего времени или секунд. Обратная совместимость snake_case пока остаётся в парсере.

Регрессии: `tests/Controller/OrderControllerTest.php` покрывает полный двухшаговый JSON-путь, сохранение позиции/доставки/наценки, очистку сессии, неверный состав, запрет подмены черновика и повторной записи. `tests/Application/Middleware/RequestDtoParserTest.php` — вложенные типы, точные строки и даты. `tests/JavaScript/json_form.test.mjs` — сериализацию формы, JSON-транспорт, CSRF-заголовок и ошибки; запуск: `node --experimental-default-type=module --test tests/JavaScript/json_form.test.mjs`.

## Отображение продукции

Ошибки JSON-форм создания, заказчика и редактирования показываются в общем
role=alert с классом error: красный текст (#d00000), выравнивание слева.
Это относится и к конфликту версии; скрытый пустой блок не занимает место.

Экран состоит из строки выбора `Наименование → Цвет/вариант → Количество → Цена → Скидка → Сумма`. Режим БН управляет отображением дополнительной цены:

- `0` — базовая цена и сумма;
- `ФОП` — цена с выбранной наценкой ФОП, итог включает наценку;
- `НДС` — цена с НДС, итог с БН включает 20%.

Поля `Цена с НДС` и `Цена с наценкой ФОП` редактируемы. При ручном вводе специальная цена переводится в базовую цену позиции, скидка позиции сбрасывается в ноль, затем форма пересчитывает остальные цены и итог.

Таблица имеет фиксированную полезную ширину и обёртку с горизонтальной прокруткой: на узком экране колонки не сжимаются и подвал с итогами не разваливается.
