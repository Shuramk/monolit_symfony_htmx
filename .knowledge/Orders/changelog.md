# Журнал заказов

`Domain/Order/Services/OrderChangelog` подключается в use case через конструктор.

Для создания: `created($orderId, $orderDto, $userId, $now)`.
Для остальных операций: `record($orderId, $event, $message, $userId, $now, $context)`.
Вызов выполняется **в транзакции изменения заказа**. Ошибка журнала откатывает заказ.
SQL находится только в `OrderChangelogRepository`, соединение — app.

## Хранение

Таблица `order_changelog`: `id`, `order_id`, `event`, `message`, `snapshot` (JSON),
`user_id`, `created_at`. Одно событие — одна строка; сообщение не входит в JSON.
Журнал только дописывается; методов изменения снимка нет.

Снимок v1 содержит номер и статус, заказчика, позиции (ID, исторические названия,
единицы, количество, сохранённую цену после скидки, эффективную цену с наценкой,
сумму), адрес/дату/стоимость доставки, наценку, суммы, комментарий, контекст.
Для `created` контекст включает введённые цены и скидки по позициям.
Цены и количества — decimal-строки; суммы считаются существующим калькулятором с Decimal.
Основные данные читаются из уже сохранённого заказа, не из текущих справочников.
Способ доставки и перевозчик пока не представлены моделью: нулевая стоимость
не трактуется автоматически как самовывоз.

HTML не сохраняется. Twig экранирует значения при выводе. JSON не пересчитывается
при открытии карточки, поэтому изменения заказов/справочников не меняют прошлые события.

В карточке снимок по умолчанию свёрнут в нативном `details` без атрибута `open`.
Сообщение события и автор находятся в `summary`: клик либо Enter/Space с клавиатуры
раскрывает и повторно сворачивает снимок без JS и запросов. Записи без снимка
выводятся обычным текстом, без пустого переключателя.

Для создания раскрывается полный состав; для редактирования — список изменений.
Под ним отдельно свёрнут «Полный снимок» с одинаково отступающими блоками до/после.
Diff вычисляется read model из неизменяемого JSON, миграция старых записей не нужна.

## Проверенное поведение legacy

`classes/Order.class.php::save_edited_order()` (строки 789–801, 900–905):
изменение цен существующих товаров сохранялось отдельным событием «Изменены цены на товары».
Добавления/удаления, количества, доставка, БН, комментарий и другие поля — отдельным
«Заказ редактировался». Если менялись обе группы, появлялись обе записи; если только
цены — только ценовая. Детали — PHP-serialized строки в editing_log по oscID.
В новом пока одно событие updated с общим diff; разделение на два типа не внедрено.

## Совместимость

Импортированный `order_status_history` остаётся без изменений. Карточка объединяет
старые записи и новый журнал по времени. Новые события не дублируются в старой таблице.
Миграция `Version20261007120000` создаёт только новую таблицу в app-базе.
Legacy только читается; импорт старых сериализованных снимков из отдельной таблицы
editing log не входит в этот шаг (старые сообщения уже импортированы).

`legacy:import-orders` отказывается выполнять полную пересборку, если существует
хотя бы одна запись нового журнала: иначе DELETE orders каскадно уничтожит события
и созданные в Symfony заказы. Для последующего обновления из legacy нужен отдельный
недеструктивный сценарий импорта; защиту обходить нельзя.
