# Добавление оплаты за продукцию

## Добавление оплаты за доставку (2026-10-09)

- `POST /orders/{id}/delivery-payments`: тот же DTO суммы/карты/UUID, отдельное право 227
  плюс общее право просмотра 220 и сессионный CSRF. Отменённый заказ запрещён.
- Кнопка под итогами доставки открывает ту же компактную форму с заголовком
  «Внесение оплаты за доставку». Карта доступна только без БН/ФОП.
- Общий AddOrderPayment работает в режиме shipment; сущность проверяет ограничения,
  добавляет платёж и повышает версию, но не увеличивает prepayment продукции.
- Новые доставки имеют source=application_shipment, старые source=shipment.
  Общая последовательность order_payment_numbers предотвращает пересечение новых ID.
  Имеющейся схемы достаточно: новых колонок/миграций/повторного импорта не требуется.
- UUID учитывает тип платежа: перенос UUID между оплатой продукции и доставки запрещён.
- money_taken=1: расходная касса не пополняется, передача/инкассация остаются отдельным этапом.
- История delivery_payment_added: «Внесена оплата за доставку X грн», карта/БН.
  С 2026-10-11 без полного снимка: сохраняется только context платежа.
- Карточка и печать суммируют обе разновидности доставки; платежи продукции учитываются
  через prepayment, без двойного суммирования. Обе формы используют существующий JS.
- HTTP-тест проверяет CSRF/право 227/валидацию/карту/БН/отмену/UUID, карточку и печать,
  смешанные старые и новые оплаты, отсутствие двойного учёта. Тест транзакционного отката
  включает оба вида новых оплат. Все SQL-фикстуры откатываются.
- Проверка после добавления доставки: 45 связанных PHP-тестов (317 assertions),
  32 JS-теста, Twig/container lint и production cache warmup прошли. Новые реальные
  оплаты не создавались; legacy остаётся только для чтения.

Перенесено 2026-10-09. Legacy только читается, кассовых движений при добавлении нет.

## Поведение

- `POST /orders/{id}/payments` принимает JSON `amount`, `operationId` (UUID), `toCard`.
- Общая защита просмотра 220 и дополнительное право операции 228; общий сессионный CSRF.
  DTO и автор подставляются по типу, SQL в контроллере нет.
- «Добавить оплату» открывает компактный dialog: «Внесение оплаты за плитку», сумма,
  «грн», карта только при markup=0, «Сохранить». Без поясняющих текстов; закрытие
  крестиком/Escape. При ошибке ввод и UUID сохраняются; одновременная отправка блокируется.
- Суммы остаются строками; до 10 целых/2 дробных знаков, минимум 0.01; запятая
  в форме преобразуется в точку. Отменённый заказ запрещён; переплата разрешена как legacy.
- Order.addPayment проверяет бизнес-правила, увеличивает prepayment, добавляет OrderPayment
  в коллекцию и повышает edit_version (старое редактирование после оплаты требует обновления).
- Use case блокирует заказ и одной транзакцией сохраняет оплату/итог/версию/changelog.
  Повтор UUID с тем же заказом/автором/суммой/картой не записывает ничего ещё раз.
  UUID с другим содержимым отклоняется. Индекс UUID дополнительно защищает БД.
- История: «Внесена оплата X грн», дополнительно БН/карта; OrderChangelog сохраняет
  только контекст платежа, без полного состава заказа. Карточка и печать учитывают prepayment, поэтому
  повторно суммировать новые OrderPayment поверх prepayment не нужно.

## Где деньги

`money_taken`: 1 — ещё не забраны; 3 — переданы в расходную кассу; 2 — забраны/проинкассированы.
NULL из legacy сохраняется как NULL. Новая оплата всегда 1, включая карту/БН как в legacy.
`to_card` и `payment_markup` — отдельные признаки, не состояния денег.

Добавление не создаёт записи в кассовом журнале и не увеличивает расходную кассу.
Передача/инкассация и UI раздела касс пока не перенесены: это отдельный этап.

## Схема и импорт

- Version20261009120000 добавляет nullable money_taken/to_card/payment_markup,
  metadata_imported_at и уникальный operation_id.
- Новые записи имеют source=application; source_id выдаётся order_payment_numbers,
  поэтому номера не пересекаются с legacy source=order/shipment.
- `legacy:import-payment-metadata` обновляет только признаки уже существующих импортированных
  оплат с metadata_imported_at=NULL. Проверяет источник/id, заказ, сумму, дату;
  несовпадение откатывает перенос. Повтор не перезаписывает признаки, даже если деньги позже забрали.
- Применено к 21 678 платежам. До/после: 21 678 оплат, сумма 366 605 636.97;
  14 081 заказ, сумма prepayment 359 962 946.37. Суммы и число записей не изменились.
- Первичный legacy:import-orders тоже сохраняет признаки, но повторный полный импорт
  на текущей базе НЕ запускался; его прежняя защита созданных заказов сохранена.

## Проверки

OrderPaymentControllerTest: JSON/права/CSRF/суммы/отмена/карта/БН/повтор/история/печать/откат.
LegacyPaymentMetadataImporterTest: точность восстановления, сохранение сумм и локальных
состояний, повтор и откат при несовпадении. Исторические refund-фикстуры OrderTest
гидратируются без конструктора новой оплаты, как Doctrine.
JS-тесты проверяют суммы без float и некорректные значения. Chrome: dialog, автофокус,
русская валидация и сохранение UUID/ввода после закрытия. Реальные оплаты в браузере
не создавались; HTTP-сценарии выполнялись на фикстурах с откатом.

Итог проверки: связанные 42 PHP-теста и 32 JS-теста прошли; Twig/container/prod cache
проверены. Полный PHP-набор: 192 теста, прежние 7 проблем вне оплаты (доступность
продуктов в старых фикстурах и жёсткий счётчик каталога 1677 вместо 1678).
Новые сценарии оплаты и переноса признаков в полном наборе тоже прошли.

2026-10-11: полные снимки создаются и отображаются только для created/updated.
У ранее записанных оплат снимки скрыты при чтении, без удаления исторических данных.
HTTP-тест проверяет новые оплаты обоих типов и четыре ранее записанных вида событий.
