# Список заказов

`GET /orders`, доступ по division 220. Данные только из application database.
Верх страницы повторяет original orders_list.tpl: кнопка создания слева (200px,
жирный шрифт 17px), поиск рядом с отступом 400px от кнопки, а не у правого края окна;
раскрываемые фильтры по статусам/менеджерам, цветные подписи выбранных
статусов и пагинация над таблицей. Шрифт таблицы 16px, строки 21px, padding 5px 14px;
минимальная ширина таблицы 1500px с горизонтальной прокруткой на узком экране.

## Фильтры и страницы

- q: номер, покупатель или телефон; debounce 300ms.
- statuses[]: строковые значения OrderStatus; по умолчанию new, in_progress,
  ready_for_shipment, delivered, partially_shipped (как на оригинале).
  Закрытые и отменённые доступны в раскрываемом фильтре. Пустой выбор даёт пустой список.
- managers[]: ID менеджеров; пустой выбор не ограничивает менеджеров.
- page: по 50 заказов, по умолчанию сортировка по номеру DESC. Количество/страницы рассчитываются
  с теми же фильтрами; номер страницы ограничивается существующим диапазоном.

OrderListView собирает OrderListPageDto; SQL находится в OrderViewRepository.
Параметры остаются в URL, ссылки страниц сохраняют фильтры. HTMX обновляет общий
фрагмент _list (контролы, подписи, страницы и таблицу), а не только tbody.
Обычный GET и восстановление истории браузера возвращают полную страницу.
Фильтры работают обычной GET-формой также без JavaScript.

## Заголовки и сортировка

Заголовки в одну строку (white-space: nowrap), семантические th; ширины колонок
соответствуют оригиналу, в том числе номер 130px и лояльность 110px.
Кликабельны те же пять колонок, что в legacy: номер, дата заказа, дата доставки,
покупатель, статус. Активная колонка показывает стрелку и aria-sort.
URL-параметры sort=id|createdAt|desiredAt|customer|status и direction=ASC|DESC.
OrderListSort ограничивает допустимые колонки; неизвестные значения дают id/DESC,
SQL не строится из произвольных параметров. Статусы сортируются в прежнем порядке
1–7, не по английским строковым значениям enum. При совпадении значений дополнительная
сортировка id DESC сохраняет стабильность пагинации.

Клик переключает направление, сохраняет q/statuses/managers/search, сбрасывает
страницу на первую. Пагинация, обычные фильтры и расширенный поиск сохраняют сортировку.
HTMX обновляет весь фрагмент списка; ссылки работают и без JavaScript.
Изменения только в чтении/шаблонах/CSS, миграции и изменение данных не требуются.
OrderListViewTest проверяет обе стороны сортировки каждой колонки, вторую страницу,
фильтры и недопустимые параметры; OrderControllerTest — переключение ссылками,
сохранение критериев и состояние HTMX-фрагмента.

## Расширенный поиск

Нажатие на «Поиск заказа» раскрывает отдельную GET-форму, как в orders_list.tpl.
Быстрый поиск справа остаётся отдельным полем. Расширенная форма задаёт
search[orderId], search[customer], search[phone], search[address], search[parentId],
search[productId], search[quantity] и statuses[]. Текстовые поля ищут подстроку;
условия объединяются через AND. Телефон ищется также среди трёх телефонов связанного
клиента. Продукт — группа, цвет — её вариант; при смене группы вариант сбрасывается.
Вариант имеет приоритет над группой (как в legacy).

Количество повторяет get_searched_orders_list: строго больше quantity−5 и меньше
quantity+5, на той же строке, что выбранный товар. EXISTS не размножает заказы.
Пустой выбор статусов расширенного поиска означает все семь статусов, а не только
пять открытых из обычного списка. Поиск начинает новую выборку без прежнего менеджера/q.
Последующая пагинация и фильтры сохраняют критерии в URL; «Сбросить» возвращает обычный список.
SQL — OrderViewRepository, сборка данных и вариантов — OrderListView и ProductCatalogRepository.
Legacy не читается при поиске, схема/данные не изменяются.

## Менеджер заказа

Оригинальный источник — sklad_orders.userID, не автор последнего изменения.
Миграция Version20261007140000 добавляет nullable orders.manager_id и индекс.
FK на identity_users намеренно нет: старый менеджер может отсутствовать среди
перенесённых пользователей. В этом случае список показывает «Пользователь #ID».
Создание нового заказа сохраняет ID текущего пользователя; редактирование не меняет менеджера.
Полный импорт заказов также переносит userID, но повторно запускать его поверх живых заказов нельзя.

Для уже перенесённых заказов: `php bin/console legacy:import-order-managers`.
Команда только читает legacy и заполняет отсутствующие manager_id у существующих
заказов. Не удаляет данные, не меняет суммы, состав, версии, журнал или заданного менеджера.
Локально миграция применена; manager_id заполнен у 14005 заказов.

Проверки: OrderListViewTest (поиск, статусы, менеджеры, count, страницы/границы),
OrderControllerTest (полная/HTMX-страница и запись менеджера при создании),
ImportLegacyOrderManagersCommandTest (ограниченное обновление и отсутствие записей в legacy).
Расширенный поиск покрыт также проверками сочетаний полей, дополнительных телефонов,
строгих границ ±5, группы/варианта и отсутствия дублей, сохранения формы и закрытых заказов;
OrderSearchDtoTest проверяет нормализацию и валидацию, order_search.test.mjs — смену
цветов и закрытие popup. После изменения: 133 PHP-теста / 778 assertions и 9 JS-тестов.
