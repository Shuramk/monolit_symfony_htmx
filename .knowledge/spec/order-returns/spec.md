# Возвраты заказа: заявки и приёмка товара

**Дата:** 2026-10-16  
**Версия:** 1.0  
**Статус:** Первый этап реализован. Кассовое проведение и возврат денег вне этапа.

## Цель и границы

Перенести заявки на возврат, приёмку товара на склад и просмотр возвратов в новую
application-базу. Не объединять физическое возвращение товара и выдачу денег.
Legacy остаётся только источником чтения; переключение production не входит в этап.

Входит:

- импорт заявок, возвратов и их позиций с сохранением исходных ID и финансового состояния;
- создание заявки без обязательной связи с заказом, активные заявки и архив;
- выбор заказа, приёмка по заявке или напрямую, складской приход и история;
- отображение принятых и проведённых возвратов в карточке заказа;
- права, CSRF, точные количества, транзакции, конкурентный доступ и идемпотентность.

Не входит:

- проведение возврата по кассе (`did=210`) и возврат только денег (`did=211`);
- новые отрицательные отгрузки, уменьшение позиций заказа и предоплаты;
- кассовые расходы, инкассация, передача денег;
- отмена приёмки или изменение уже принятого возврата: отдельный контракт компенсации.

## Подтверждённое поведение legacy

- `modules/admindirector.php`, `case 114/115`: заявка содержит продукцию,
  количества, комментарий, автора, дату и `done`; заказ ещё не выбран.
- `case 102/103`, `templates/order_return.tpl`: выбор заказа, приёмка напрямую
  или с заполнением количеств из заявки. В шаблоне приёмка доступна группам 1/2/3.
- `Order::add_return_from_order()` добавляет положительные количества в `storage2`,
  пишет складскую историю, создаёт возврат, позиции и событие заказа.
  Цена позиции сохраняется из `order.products[productID].newPrice`, не из каталога.
- Приёмка сама по себе не изменяет `order_items`, итог отгрузки и предоплату.
  Запись в changelog с `statusID=5` не равна обновлению статуса самого заказа.
- `Order::get_order_list_returns()` выбирает непроведённые возвраты по `userID IS NULL`.
  `get_order_list_allreturns()` возвращает все возвраты заказа.
- `modules/route_orders.php`, `case 210`: отдельное проведение создаёт отрицательную
  отгрузку, уменьшает количества заказа и предоплату, записывает выплату в кассу.
  Нулевая выплата не создаёт кассовый расход, но товарная часть проведения выполняется.
- При групповом проведении legacy записывает денежную сумму в первый возврат,
  остальным — ноль. Импорт сохраняет эти значения без перераспределения.

## Архитектура

```text
HTTP → DTO → приёмка возврата → общая транзакция app
                                 ├─ заказ: блокировка и проверка версии
                                 ├─ заявка и возврат с позициями
                                 ├─ товары: остатки и складская история
                                 └─ история заказа

GET → ReadModel → Repository → DTO → Twig/HTMX
legacy SELECT → импорт → новые таблицы app (без складских движений)
```

SQL размещается только в Repository. Использовать существующие
`OrderRepository::transactional()/findForUpdate()`, `ProductRepository`,
`Product::changeStock()`, `WarehouseRepository` и `OrderChangelog`.
Операция возврата координирует их внутри одной транзакции: не вызывать отдельно
универсальный приход для каждой позиции с самостоятельным завершением операции.
`ShippingRepository::orderSource()` уже читает итог отгрузок из
`order_shipments/order_shipment_items`; не брать количество из активных задач.

Реализованные компоненты:

- `Domain/Order/Repository/OrderReturnRepository`, `OrderReturnImportRepository`;
- `Domain/Order/UseCases/OrderReturns` (`draft`, `accept`) и `Dtos/OrderReturnDto`;
- `Domain/Order/ReadModel/OrderReturnsView` и DTO страниц/строк;
- `Application/Controller/Warehouse/OrderReturnsController`;
- `Application/Command/ImportLegacyOrderReturnsCommand`.

## Функциональный контракт

### Заявки

Маршруты: `GET /warehouse/returns`,
`GET /warehouse/returns/archive`, `POST /warehouse/returns/drafts`.
Список показывает активные заявки и непроведённые возвраты раздельно:
это разные состояния и разные объекты.

Создание принимает JSON с `operationId` (UUID), `comment` и `items`:
`[{"productId":123,"quantity":"2.500"}]`.
Автор и время определяются сервером. Нулевые/пустые строки пропускаются,
отрицательные и некорректные отклоняются, пустой итоговый состав запрещён.
Повторяющиеся товары нормализуются до одной строки; проверка выполняется после
суммирования. Используются существующие товары, не группы каталога.

### Приёмка

Маршруты: `GET /orders/{id}/returns/new`,
`POST /orders/{id}/returns`. JSON: `operationId`, `orderVersion`, nullable `draftId`,
`items: [{"productId":123,"quantity":"2.500"}]`.
Успех возвращает JSON с `id` созданного возврата; повтор того же запроса — тот же ID.

- Товар должен присутствовать в выбранном заказе; не принимать цену и автора от клиента.
- Приёмка по отменённому заказу запрещена на сервере, независимо от наличия заявки.
  Состояние проверяется под блокировкой заказа; ошибка не меняет заявку и остатки.
- Количества рассчитываются через существующий `Decimal`, без float, до 3 знаков
  как в текущих складских операциях. Импортированные количества сохраняются точно.
- Приёмка направлена в Цех (`storage_workshop`, legacy `storage2`), без выбора склада.
- Зафиксировать цену на момент приёмки из модели заказа с проверкой соответствия
  legacy `newPrice`. Один товар в заказе не должен иметь разные цены. Если исторические
  данные нарушают этот инвариант, приёмка соответствующего товара отклоняется
  с понятной ошибкой, без усреднения, выбора `MAX(price)` или автоматического
  исправления заказа. Повторяющиеся позиции с одинаковой ценой можно агрегировать.
- В одной транзакции: принять возврат и позиции, увеличить остатки, записать историю,
  отметить связанную заявку выполненной, записать событие заказа и повысить его версию.
- У заказа остаются прежние позиции, предоплата, отгрузки и статус. Повышение версии
  защищает от устаревшего редактирования и повторной конкурентной приёмки.
- Заявка служит предварительным заполнением: как в legacy, фактически принимаемые
  количества могут отличаться. Сохранить связь и снимок фактического состава.
- По одной заявке допускается одна успешная приёмка; при ошибке она остаётся активной.

### Согласованное ограничение количества

Для пары заказ/товар:

```text
доступно к возврату = SUM(количеств фактических отгрузок, включая отрицательные)
                     − SUM(принятых, но ещё не проведённых возвратов)
```

Пример: отгружено 10, принято 3, но не проведено → доступно 7.
После проведения: отгрузки содержат 10 − 3, непроведённых нет → снова доступно 7.
Вычитать все исторические возвраты из итоговой отгрузки нельзя: проведённые будут
учтены дважды. Заявки, ещё не принятые на склад, количество не резервируют.

Запретить новую приёмку сверх доступного; отрицательное историческое значение
показать как несоответствие, не исправлять автоматически и не разрешать новый приход.
Это новая серверная защита: в legacy-методе явной проверки лимита нет.
При добавлении кассового проведения сохранить ту же формулу и блокировку заказа.

### Просмотр и безопасность

- В карточке заказа под существующим правом 220 показывать дату, автора приёмки,
  состав, сохранённую цену и состояние проведения; исторические сумму, автора
  и дату проведения показывать отдельно от товарной стоимости.
- На этапе 1 нет кнопки выплаты или проведения, меняющей только часть данных.
- Все записи требуют аутентификации, существующего сессионного CSRF и отдельного
  права операции; заявка, просмотр и приёмка проверяются отдельно на сервере.
- Права привязать к legacy 114/115 и 102/103 после сверки фактических разрешений
  и mapping ролей. Не подменять их общим правом складского прихода и не расширять
  доступ ролям, которым legacy-форма недоступна.
- Блокировки: заказ → заявка при наличии → товары по возрастанию ID.
  Приёмка и будущее проведение обязаны сериализоваться через тот же заказ.
- Проверять повтор `operationId` до сравнения устаревшей версии: точный повтор
  возвращает прежний результат, другой состав/заказ/автор/заявка отклоняется.

## Данные и импорт

Новые таблицы: `order_return_drafts`, `order_return_draft_items`,
`order_returns`, `order_return_items`; add-only миграция только app.

- Заявка: ID, автор, дата, комментарий, признак выполнения, nullable связь с приёмкой,
  уникальный nullable ключ новой операции, исходные данные импорта.
- Возврат: ID, order_id, nullable draft_id (UNIQUE для новой связи), accepted_at/by,
  nullable processed_at/by, refund_amount DECIMAL, operation_id UNIQUE NULL,
  снимок запроса и исходных данных. Исторически выполненная заявка может не иметь
  восстанавливаемой связи с возвратом: не придумывать её.
- Позиции: ID, ссылка на родителя, product_id, quantity DECIMAL(15,3),
  price DECIMAL(19,4) для принятого возврата; исходные идентификаторы/данные сохраняются.
- Индексы: возвраты по заказу и ID, состояние проведения, элементы по родителю/товару,
  заявки по состоянию/дате. Не вводить уникальность товара для исторических строк
  без проверки фактических дубликатов.
- ID новых записей выдаются после импортированного диапазона. Импорт не использует
  удаление и полную пересборку уже работающих application-таблиц.

Источники: `sklad_order_returnDraft`, `sklad_order_returns`,
`sklad_order_returns_carts`. Сохранять авторов, даты, денежные суммы, `done` и
nullable признаки проведения без пересчёта. Исходную точность и часовой пояс сверить
с существующими импортёрами. Повтор импорта не перезаписывает новые состояния.

Импорт не добавляет складских движений и не меняет количества заказов, отгрузки,
предоплату, кассу и существующую историю: эти последствия уже отражены в снимках.
До записи проверить отсутствующие заказы/товары/авторов, дубликаты и противоречивые
признаки проведения. Несоответствия вывести в отчёт, не создавать фиктивные сущности.
Сверить количества строк, количества продукции, цены, суммы и состояния по ID.
DDL up/down и конкретные nullable/FK ограничения определить после этой сверки,
не принимать destructive down за допустимый откат с уже созданными возвратами.

## Проверки

- Прямая приёмка и приёмка по заявке, расхождение с предварительным составом.
- Неотгруженный товар, частичная отгрузка, несколько приёмок, отрицательная отгрузка
  уже проведённого возврата; формула не вычитает проведённые позиции повторно.
- Две конкурентные приёмки не превышают лимит, повтор UUID не удваивает остатки.
- Ровно доступный остаток принимается; превышение отклоняется без побочных записей.
- Отменённый заказ отклоняется и при прямой приёмке, и при приёмке по заявке.
- Разные цены одного товара в историческом заказе не усредняются: приёмка этого
  товара отклоняется; одинаковые цены допускают агрегацию количеств.
- Ошибка второй позиции откатывает первую, заявку, историю и версию заказа.
- Цены 4 знака, количества 3 знака, дробные значения и отключённый товар заказа.
- GET ничего не меняет; права и CSRF проверяются HTTP-тестами.
- Повтор импорта сохраняет новые записи; остатки, предоплата и отгрузки до/после
  импорта неизменны. Исторические возвраты с нулевой выплатой не становятся pending.

## Согласованные решения

1. Приёмка сверх фактически отгруженного остатка с учётом непроведённых возвратов запрещена.
2. Приёмка по отменённому заказу запрещена.
3. Один товар в заказе не должен иметь разные цены; автоматический выбор цены
   для противоречивых исторических данных не допускается.

## Результат технической сверки

Права: список приёмки 102, запись 102+103 и роли Main/Sales/Production;
заявки и архив 114, создание 114+115. Право 115 восстановлено из связи 114→115
существующего LegacyPermissionExpander. Карточка заказа остаётся под правом 220;
приёмка доступна складскому пользователю без права просмотра полной карточки.

Импортировано 5354 возврата, 6059 позиций и 1282 заявки. Найдены 30 возвратов без
существующего заказа, 4 позиции без возврата, 65 отсутствующих авторов приёмки,
5021 отсутствующий автор проведения (включая исторические служебные ID),
23 некорректные позиции заявок. Противоречий между nullable датой/автором проведения нет.
Исходные данные сохранены без выдуманных связанных объектов; для исторических
ссылок намеренно не добавлены внешние ключи. Новые ссылки проверяются прикладным кодом.
Некорректные позиции заявок остаются в исходном payload и отчёте; в UI заявка
помечается предупреждением. Существующие данные не исправляются автоматически.
